# 按平台设计问题与来源审计

版本：2.0.0。官方资料核对日期：2026-11-06。

本版将“同一关键词同时发给全部平台”改为“为每个平台独立设计、预览和选择问题”。平台策略保存在 [platform_strategy_catalog.json](../platform_strategy_catalog.json)，其中包含六个平台的已确认能力、证据链接、适用范围、限制和问题模板。修改策略后，仍需通过实际回答和原始引用验证效果。

## 为什么这样分工

不同产品的公开能力和可访问内容存在差异，但不能将其简化为“每个 AI 只看一家网站”。本项目区分两类内容：

- **官方能力**：能从平台自己的帮助、用户协议、产品发布或官方报告核实的功能。
- **提问策略**：项目为本公司的业务选择的研究方向。这是待验证的默认设置，可以调整，不是平台公布的信源权重或推荐算法。

| 平台 | 默认方向 | 官方证据及其适用范围 | 不作出的推断 |
| --- | --- | --- | --- |
| 豆包 | 消费场景、常见疑问、产品信息 | 用户协议第 2.2.2 条描述对第三方公开网页的检索及来源展示，适用于豆包服务。[用户协议](https://www.doubao.com/legal/terms) | 不认定固定优先抖音，不将消费者分享当作产品检测。 |
| DeepSeek | 证据对照、矛盾与缺口 | 官方发布确认网页端联网搜索及复杂问题的多关键词检索。这是历史功能发布，不能用其中旧的 API 状态判断当前 API 能力。[官方发布](https://deepseek.com/news/v2-5-final/) | 不认定固定依赖百度、知乎或某家数据库。 |
| Kimi | 长文、公开文档、研究资料目录 | 官方帮助说明搜索引擎、垂直数据库及来源链接等能力，具体调用由产品按问题判断。[搜索帮助](https://www.kimi.com/help/features/search) | 不保证每次联网，不声称已经读过未上传或不可访问的文件。 |
| 千问 | 商品规格、店铺主体、购买决策 | 阿里巴巴官方发布介绍千问 **App** 与淘宝互通及商品发现、比较能力；这是 App 功能范围。[官方发布](https://home.alibabagroup.com/zh-HK/document-1991231293551017984) | 不认定千问网页端/API 每次都调用淘宝，不把店铺自称当作授权证明。 |

## 三类问题分别用途

### 自然发现

以真实客户问题观察自然出现的品牌、企业和链接。此类问题不注入公司名称、品牌名称、官网地址，也不指示只从公众号、知乎等某渠道检索。例如同一个“益生菌食品合作”主题，可以分别生成：

| 平台 | 问题侧重点 |
| --- | --- |
| 豆包 | 门店面对消费者时应解释哪些产品信息。 |
| DeepSeek | 合作选择的不同观点、事实依据和信息缺口。 |
| Kimi | 合作调研报告需要收集什么资料。 |
| 千问 | 商品规格、店铺主体和售后条款如何对照。 |
| 腾讯元宝 | 品牌介绍、招商介绍与实际运营主体如何区分。 |
| 知乎直答 | 从业者经验与可核实事实的边界。 |

这些问题具有不同用途，不能将结果直接做成同一道题的跨平台推荐排名。比较时必须保留完整问题、目标、时间、通道和来源。

### 品牌核验

允许明确写入已确认的品牌、公司和业务信息，检查 AI 能否准确理解主体与产品。它可以帮助发现同名、主体误认或合作关系误写，但带品牌提示的结果不计为自然发现。

本公司的已确认表述为：**“广微 益森日纪”是广州菌和生物科技有限公司与广微集团合作的品牌；广州菌和主要从事品牌运营和招商。** 该信息用于提问时应作为待核实对象，不能把企业自己的陈述自动标记为独立证明。尚未确认的生产主体、授权文件和资质不得补写；官网备案期间也不能声称网站已可访问或已被平台收录。

### 来源审计

允许提出特定来源方向，例如检查元宝是否能够找到公开公众号原文，或让知乎直答追溯原始回答。必须记录实际找到的作者/发布主体、标题、日期、URL、可访问情况及证据缺口。没有找到就保存“未找到”，不得替换成猜测的账号、链接或文件。

这类问题包含来源指令，属于受引导样本，单独统计，不进入自然品牌发现比例。提出“搜索公众号”只表示本次请求；返回链接和原文才是实际来源证据。

## 操作流程

1. 输入主题，选择参与的平台和目标；生成的是问题草稿，尚未向平台发送。
2. 分别检查每个平台的问题、设计理由与来源方向。每个问题可独立编辑、保留或删除。
3. 确认发送清单。每一行只对应一个平台，不生成“关键词 × 平台”的全部组合；相同问题分配多个平台会提示修改。
4. 保存回答时保留原问题、通道、目标、策略版本和引用。回答校验只确认采集完整性及对应关系，不表示事实、疗效、授权或排名已经核实。
5. 根据真实返回来源调整平台问题池。日计划保存的是具体问题与平台的快照；旧的统一分发计划保留记录并停用，不自动重启。

关键词库按平台保存。来源审计适合核查“已有内容是否能被找到”，自然发现适合观察“不提示品牌时是否出现”，品牌核验适合检查“被直接询问时是否说对”。三者的数据用途不同。

## 实际落地内容准备

本工具管理问题、连接、观察和证据。它不自动取得第三方账号的发布权限，也不会因为连续提问就改变模型训练数据。企业需要另行维护真实、可公开访问的资料：

- 微信公开内容：核实账号主体；介绍品牌关系、运营企业、产品事实与合作联系方式；保留原文日期。视频内容应有可引用的事实说明，不虚构账号或播放量。
- 企业与文档资料：明确品牌、运营、生产、经销职责；原始文件标明适用产品、版本、日期和授权范围。
- 商品信息：统一名称、净含量、配料标签、储存条件、店铺主体及售后条款；避免不同页面的字段互相矛盾。
- 问答内容：回答真实客户疑问，注明商业身份；经验、企业自述与独立事实分别表述，不制造虚假第三方背书。

对于益生菌食品，问题模板围绕产品信息与合作核查，不生成治疗承诺、没有依据的健康效果、假资质或“第一品牌”式排名结论。发布前依据本公司已确认资料复核，不能用 AI 回答替代产品事实材料。

## 配置与维护

目录文件每个平台包含 `id`、`focus`、`summary`、`evidence_level`、`capability_facts`、`sources`、`strategy_hypothesis`、`source_guidance`、`source_prompt`、`caveat` 和 `templates`。

- `sources[].scope` 明确说明帮助、协议、消费端发布、开发者 App 描述、投资者报告或搜索服务/API 的证据范围。
- `source_prompt` 只用于来源审计，不作为自然发现的隐藏引导。
- `templates` 为三个目标分别提供五个不同的问题草稿。占位符为 `{topic}`、`{business}`、`{brand}`、`{company}`、`{domain}`；自然发现只使用主题与业务信息。
- `verified_on` 是本项目检查页面的日期，不是对产品未来行为的保证。产品更新后应重新检查原始来源。

需要验证的是“实际回答用了什么、原文能否访问、主体关系是否准确”，而不是把渠道猜测写成固定算法。任何一家平台都不能由本项目保证优先推荐、永久收录或关键词霸屏。
